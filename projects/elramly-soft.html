Project Overview

This educational lab applies Linux administration concepts to a small-business scenario. Work is organized into documented tasks: inspecting the server before making changes, then managing department accounts, shared directories, and administrative privileges.

Status: The project evidence marks the baseline and Linux administration phases complete. Service deployment, monitoring, backup, recovery, and further end-to-end testing remain planned; no completion claim is made for those items.

Implementation Phases

Phase 1 — Server baseline inspection Completed

  • Identified the operating system, release, hostname, and VirtualBox environment.
  • Inspected interface and IP configuration, default route, DNS, and NetworkManager profile.
  • Reviewed partitions, filesystems, mount points, and utilization without changing storage configuration.
  • Verified that NetworkManager, sshd, and firewalld were active and enabled at the time of inspection. Firewall rule correctness and SSH hardening were not tested as part of this phase.

Phase 2 — Linux system administration Completed

  • Created four department groups and 12 corresponding employee accounts. The written task calls the IT group it, while captured terminal evidence uses infrastructure; the repository should reconcile that naming difference.
  • Organized department shares beneath /srv/company/ with group ownership and SetGID permissions. A 0007 umask was documented to prevent default access for others.
  • Applied and inspected access/default ACLs for the development share, including the documented oroberts exception.
  • Documented role-based sudo: oroberts in wheel, limited selected command access for mwilliams, and no sudo assignment for snguyen.

Next work Planned

Technical Considerations & Decisions

  • Bridged networking: The VM appears as a separate device on the physical LAN, so any future static address must be checked against the LAN subnet and DHCP range. The documented address remains redacted.
  • Storage baseline first: Separate /, /boot, and /home filesystems were inspected before planned service work; no storage changes were made during inspection.
  • Shared department access: SetGID supports group inheritance for new files, while the documented umask 0007 removes permissions for other users. ACL masks and default ACLs still need to be considered when validating effective access.
  • Least-privilege administration: The sudo design separates full administrator, limited technician, and standard-user roles. The project documentation calls for checking sudoers syntax with visudo -c and reviewing each account's allowed commands.

Lessons Learned

  • A system baseline makes later configuration and troubleshooting easier to reason about.
  • Linux groups, directory ownership, SetGID, umask, and ACLs work together to shape effective access.
  • Role-specific sudo is more precise than granting every IT user full administrative privileges.
  • Service state checks are not a substitute for validating firewall rules, SSH security, or end-to-end connectivity.
